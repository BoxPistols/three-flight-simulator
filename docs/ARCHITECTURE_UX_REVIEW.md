# アプリケーション見直し提案：目的の再定義からアーキテクチャ・UI/UX・ユーザーストーリーまで

作成日: 2026-07-10
対象: `three-flight-simulator` (main ブランチ時点のコードベース全体)

---

## 1. エグゼクティブサマリー

本アプリは「Three.js + React によるドローンのウェイポイント飛行の3D可視化」という技術デモとしては動作しているが、**「誰の・どんな課題を解決するプロダクトなのか」が定義されていない**。その曖昧さがコードにそのまま現れており、以下の症状として観測できる。

- 「緯度・経度」というラベルの入力欄に、実際にはシーン内のローカルXZ座標（15や32といった値）を入れている
- 地理座標変換ロジック（`convertLatLonTo3D` / `convert3DToLatLon`）が実装済みなのに**どこからも呼ばれていない**（デッドコード）
- ウェイポイントの `rotation` フィールドがUIで入力できるのに**飛行アニメーションで一切使われない**
- README は「FPVカメラ（ドローン目線）」と謳うが、実装は三人称追従カメラ
- サンプル経路・速度制限（20km/h）など「実務ツール」的な要素と、オンボーディングの「体験してみましょう」という「デモ/遊び」的な要素が混在

**提案の骨子**: まずプロダクトの方向性を「ドローン飛行ルートの計画・プレビューツール」として定義し（§4）、そこから逆算してユーザーストーリー（§5）、アーキテクチャ（§6）、UI/UX（§7）を再設計する。移行は3フェーズのロードマップ（§8)で段階的に行う。

## 3. 課題の全体像

### 3.1 プロダクト定義の曖昧さ（根本課題）

「シミュレーター」「プランナー」「デモ/ゲーム」の3つの性格が混ざっている。

| 観測される要素 | 示唆する方向性 |
|---|---|
| 緯度・経度・高度(m)・速度(km/h) の入力、20km/h の速度上限 | 実務の飛行計画ツール |
| FPV風カメラ、オンボーディングの「体験してみましょう」 | 体験デモ・ゲーム |
| デバッグパネル（座標・進捗のテレメトリ表示） | 開発者向け検証ツール |

どれを主目的にするかで、必要な機能・UI・データモデルが大きく変わる。**この決定が全ての見直しの起点になる**（§4で提案）。

### 3.2 アーキテクチャの課題

1. **座標系の二重定義とデッドコード**
   - `coordinateConverter.ts` に真面目な地理座標変換（地球半径ベースの平面近似）が実装されているが未使用。
   - 実際に使われる `convertWaypointsTo3D` は `longitude→X, latitude→Z, altitude×0.5→Y` の単純マッピングで、フィールド名と実体が乖離。
   - `page.tsx` のクリックハンドラでは `altitude: position[1] * 2` と逆変換スケールがハードコードされ、変換知識が複数ファイルに漏れている。

2. **型とロジックの重複**
   - `Waypoint` インターフェースが `Scene.tsx` と `WaypointEditor.tsx` で二重定義。
   - サンプル経路生成が3箇所に存在（`page.tsx`、`WaypointEditor.tsx` 内の `addSampleWaypoints`、`Scene.tsx` の未使用エクスポート約450行）。

3. **状態管理が `page.tsx` に集中**
   - waypoints / isFlying / drawer / onboarding / debug / resize までが1コンポーネントの useState に同居し、props drilling で配布。ドメインロジック（飛行計算、経路操作）とUI状態が未分離。

4. **飛行モデルの物理的整合性がない**
   - `increment = (speed × 0.3 × visualSpeed × delta) / distance` は「速度」の単位（km/h）と無関係な進捗率計算。デバッグパネルの Flight Time は実時間であり、シミュレーション時間ではない。「高度(m)」「速度(km/h)」と単位を謳う以上、シミュレーション結果（所要時間・距離）が実単位で出せないのは信頼性の欠陥。
   - `AnimatedDrone` 内で `pathPoints` が毎レンダー再生成され、それを依存配列に持つ `useEffect` が毎レンダー実行される（非飛行時にドローン位置を毎回リセット）。

5. **リポジトリ衛生**
   - `package.json` の name は `drone-simulator`、リポジトリ名は `three-flight-simulator`。
   - `pnpm-lock.yaml` と `package-lock.json` が両方コミットされている。
   - テスト・CI が存在しない。

### 3.3 UI/UX の課題

1. **オンボーディングの選択が機能していない**: 初期状態で既にサンプルがロードされるため（`useState(() => generateSampleWaypoints())`）、「自分で作成」を選んでもサンプル16点が残る。ユーザーの意思決定が無視される体験。
2. **嘘のアフォーダンス**: 3Dマーカーはホバーで pointer カーソルになるがクリックしても何も起きない（削除ハンドラ未接続）。
3. **ラベルと実体の乖離**: 「緯度 15 / 経度 32」という値は地理座標として不自然で、初見ユーザーを必ず混乱させる。
4. **3Dとテーブルの対応が取れない**: テーブルに順序番号がなく、3D空間のどのマーカーが第何ウェイポイントか照合できない。並べ替え手段もない。
5. **入力しても意味のないフィールド**: 回転スライダー（0–360°）は保存されるだけで挙動に影響しない。
6. **進捗表示が飾り**: 飛行中の LinearProgress は indeterminate で実進捗と無関係（実データは debugData にあるのに使っていない）。
7. **デバッグパネルがデフォルトON**: 一般ユーザーの初期画面に開発者向けテレメトリが常時表示される。
8. **作業成果が保存されない**: 丁寧に経路を作ってもリロードで消える。実務ツールとしては致命的、デモとしても再訪動機を失う。
9. **アクセシビリティ/入力手段**: キーボード操作・aria 対応・タッチ最適化は未着手。

### 3.4 ドキュメントと実装の乖離

README / TECHNICAL_DETAILS.md は旧実装の記述が多い（FPVカメラの lerp/slerp オフセット、クリック高度50m、ドラッグ閾値0.1、基準点ベースの座標変換など、現行コードと不一致）。ドキュメントが「あるべき姿」でも「現状」でもない中間状態で、新規参加者の混乱源になる。

## 4. 目的の再定義：3つの選択肢と推奨

| 方向性 | ターゲット | 必要になる主要機能 | 判断 |
|---|---|---|---|
| **A. 飛行ルート計画・プレビューツール** | ドローン測量/点検/空撮の事業者、飛行申請前の検討者 | 実地理座標、地図/実在地形、プラン保存・共有・エクスポート、所要時間/距離/バッテリー見積 | ⭐ **推奨** |
| B. 体験型3Dデモ/ゲーム | 一般ユーザー、ポートフォリオ閲覧者 | 手動操縦、演出強化、スコア/ミッション | 差別化が難しく既存資産（座標・速度単位・速度制限）を捨てることになる |
| C. 開発者向け飛行アルゴリズム可視化 | ドローンSW開発者 | ログ再生、API連携、テレメトリ | ニッチすぎて現UIの大半が不要になる |

**推奨は A**。理由: (1) 既存コードの「緯度経度・高度m・速度km/h・20km/h上限」という語彙は明らかにAを志向して書かれている、(2) 未使用の地理座標変換など資産が活きる、(3) デバッグパネルは「フライト情報パネル」として実務価値に転用できる、(4) B/Cと違い明確なユーザー課題（飛行前に経路を安全・効率の観点で検討したい）がある。

以降の提案はAを前提とする。**アプリの一言定義（提案）**:

> 「ドローンの自動飛行ルートを3D空間で計画し、飛行前にプレビュー・検証できるWebツール」

## 5. ユーザーストーリー（方向性Aベース）

### ペルソナ

- **P1: 点検・測量オペレーター（主要）** — 業務で飛行計画を作り、現場前に経路の妥当性（高度・障害物・所要時間）を確認したい。
- **P2: 空撮プランナー** — 撮りたい画角の経路を試行錯誤し、クライアントにプレビューを共有したい。
- **P3: 初学者/検討者** — ウェイポイント飛行の概念を安全に学びたい。

### エピックとストーリー

**Epic 1: ルート作成**
- US-1.1 オペレーターとして、3D画面クリックでウェイポイントを追加し、**追加時に高度を指定**できる（現状: 固定高度）。
- US-1.2 ウェイポイントを**ドラッグで移動**できる。
- US-1.3 テーブルとマーカーが**番号で対応**し、行ホバーで3D側がハイライトされる（逆方向は実装済み）。
- US-1.4 ウェイポイントの**順序を並べ替え**できる。
- US-1.5 マーカークリックで削除**または**選択編集ができる（現状の壊れた導線の修復＋誤削除防止）。

**Epic 2: プレビューと検証**
- US-2.1 プランナーとして、飛行を開始すると**実速度に基づく所要時間**でドローンが移動し、経過時間・残距離が実単位で表示される。
- US-2.2 カメラモードを**俯瞰追従 / FPV / 自由視点**から選べる（README の約束の実現）。
- US-2.3 総距離・総所要時間・最高/最低高度が**飛行前にサマリー表示**される。
- US-2.4 経路が建物と交差する場合に**警告表示**される。

**Epic 3: 保存と共有**
- US-3.1 プランが**自動保存**され、リロード後も残る（localStorage）。
- US-3.2 プランを**JSON/GeoJSONでエクスポート・インポート**できる。
- US-3.3 複数プランを名前を付けて管理できる。

**Epic 4: 学習・導入**
- US-4.1 初学者として、初回に**目的が伝わるオンボーディング**（「これは飛行計画ツールです」）とサンプルプランで全体像を掴める。「自分で作成」を選んだら**空の状態から始まる**。
- US-4.2 UIの座標系が**一貫した意味**を持つ（シーンモード: X/Y/Z[m]、または地理モード: 実緯度経度）。

### スコープ外の明確化（決めることが目的）

- リアルタイム手動操縦（ゲーム化） / 実機連携・実地図タイル（将来フェーズ） / マルチユーザー編集

## 6. 目指すアーキテクチャ

### 6.1 レイヤ分離

```
src/
├── app/                    # ルーティングとページ骨格のみ
├── features/
│   ├── flight-plan/        # プランCRUD・並べ替え・永続化・入出力
│   │   ├── store.ts        # 状態管理（Zustand 推奨: R3F と相性が良く再レンダー制御が容易）
│   │   ├── model.ts        # Waypoint / FlightPlan 型の唯一の定義
│   │   └── components/     # WaypointEditor, PlanSummary など
│   ├── simulation/         # 飛行エンジン（純関数）: 位置補間・所要時間・進捗計算
│   │   └── engine.ts       # UIに依存しない。単体テストの主対象
│   └── viewer/             # R3F シーン: Drone, Markers, Path, City, Cameras
├── lib/
│   └── coordinates.ts      # 座標系を型で区別（SceneCoord / GeoCoord）し変換を一元化
└── providers/
```

設計原則:
- **ドメインを純関数に**: 「時刻tでのドローン位置・向き・進捗」を `engine.ts` が計算し、R3F 側は毎フレームそれを描画するだけにする。速度(km/h)と距離(m)から所要時間が正しく出る＝US-2.1/2.3 が自然に満たせる。
- **座標系を型で固定**: `SceneCoord` と `GeoCoord` を別型にし、暗黙のスケール（`×0.5`、`×2`）の散在を廃止。まずはシーン座標に一本化してUIラベルを「X/Z座標[m]」に正し、地理モードは後続フェーズで `convertLatLonTo3D`（現デッドコード）を活かして追加する。
- **型の一元化**: `Waypoint` 定義とサンプル生成を1箇所に統合。

### 6.2 技術的な整理

| 項目 | 現状 | 提案 |
|---|---|---|
| スタイリング | MUI + Emotion + Tailwind の3系統 | MUI + Emotion に統一し Tailwind を除去（使用箇所はローディング表示程度） |
| 状態管理 | page.tsx の useState 群 | Zustand ストア（plan / simulation / ui の3スライス） |
| 永続化 | なし | ストアの persist ミドルウェア（localStorage）＋ JSON入出力 |
| テスト | なし | Vitest（engine / coordinates / plan操作）＋ Playwright スモーク1本 |
| CI | なし | GitHub Actions で lint + typecheck + test |
| ロックファイル | pnpm と npm が併存 | pnpm に統一し package-lock.json を削除 |
| ドキュメント | 実装と乖離 | README を「プロダクト定義＋現状の使い方」に書き直し、TECHNICAL_DETAILS はアーキテクチャ移行後に再生成 |

## 7. UI/UX 改善方針

1. **情報設計の再編**: サイドパネルを「①プラン管理（選択/新規/入出力）→ ②ウェイポイント一覧（番号付き・並べ替え可）→ ③プランサマリー（距離/時間/高度）→ ④実行コントロール」の階層に。
2. **座標ラベルの正直化**: 地理モード実装までは「緯度/経度」を「X座標[m] / Z座標[m]」に変更（最小コストで混乱を解消できる最重要修正）。
3. **壊れた導線の修復**: マーカークリック導線を「選択→パネルで編集/削除」に変更（即削除より安全で、pointer カーソルの嘘も解消）。
4. **オンボーディング修正**: 「自分で作成」選択時は空プランで開始。初回ダイアログでプロダクトの目的を一文で伝える。
5. **進捗の実データ化**: LinearProgress を `overallProgress` に接続し、残り時間を表示。デバッグパネルは「フライト情報」に改名して主要指標（進捗・速度・残距離・経過時間）に絞り、開発者向け詳細（座標・回転生値）は開発ビルドのみに。
6. **無意味な入力の削除**: rotation スライダーは機能実装まで非表示にする（実装しない機能を見せない）。
7. **アクセシビリティ**: 主要操作にキーボード対応（Delete で選択WP削除、Space で開始/停止など）、コントロール群への aria-label 付与。

## 8. ロードマップ

### Phase 1: 正直化と修復（〜1週間・小PR群）
目的定義の合意 → README冒頭にプロダクト定義を明記。既存バグ・嘘の解消:
- マーカークリック導線の修復（US-1.5）
- オンボーディング「自分で作成」の修正（US-4.1）
- 座標ラベルの正直化（US-4.2）
- rotation UI の非表示化、デバッグパネルのデフォルトOFF
- 進捗バーの実データ接続
- 重複コード統合（Waypoint型・サンプル生成）、デッドコード削除、ロックファイル統一

### Phase 2: 基盤再構築（1〜2週間）
- features/ 構成への移行、Zustand 導入、simulation エンジンの純関数化＋実単位の時間・距離計算（US-2.1, 2.3）
- 永続化と JSON 入出力（US-3.1, 3.2）
- Vitest + CI 導入
- Tailwind 除去

### Phase 3: プロダクト価値の拡張（2週間〜）
- カメラモード切替（US-2.2）、ウェイポイントのドラッグ移動・並べ替え（US-1.2, 1.4）
- 複数プラン管理（US-3.3）、建物交差警告（US-2.4）
- 地理座標モード（デッドコードの `convertLatLonTo3D` を活用）、将来的に地図タイル/実地形
